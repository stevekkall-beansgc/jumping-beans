# P0 write acceptance review

Date: 2026-08-31  
Scope: Terra's Watch write-hardening checkpoint after `f28091f`. Review only;
no production code was modified and nothing was deployed.

## Verdict: STOP / NO-GO

The deterministic gate and most isolated authorization/replay/redaction probes
pass. The updated engine and Watch UI correctly separate staging from commit and
the local-development seam persists a staged action into a later commit request.
P0 write acceptance is still blocked by a reproducible same-key concurrency
race: two simultaneous commits for the same action both return `committed` and
create two interest records. The local seam is not an atomic authority, no D1
or Durable Object binding exists, and the production deployment is still the
older pre-checkpoint page.

## Failed checks and remaining blockers

1. **Same-key concurrency is a P0 blocker.** `commitInterest()` performs
   idempotency lookup, grant validation, and repository commit without an atomic
   uniqueness claim. The local seam allowed two concurrent commits for the
   same action/key and created two records.
2. **The local repository is process-local and non-durable.** Stage-to-commit
   persistence passed only because both requests shared one Node module's
   in-memory maps. It is not persistence across worker isolates, restarts, or
   deployments.
3. **No authoritative production repository is bound.** `wrangler.toml`
   intentionally has no D1/DO binding, so production stage/commit fail closed;
   this is safer than silently writing locally, but it is not a shipped write
   capability.
4. **No rate limiter or CSRF/session cookie boundary is implemented.** The
   header-based session is useful for the seam but is not a production
   authentication or abuse control.
5. **No full action-receipt journey export was proven.** The Watch receipt
   shape is redacted and versioned in the isolated commit result, but the
   engine journey receipt was not linked to a Watch action in a browser.
6. **Production and local browser surfaces diverge.** The updated checkpoint is
   local-only; production remains the old implementation.

A further review note: the same-payload replay response correctly returns the
original receipt, but its internal local repository object carries a nested
`record` field. Keep returned receipts derived from an explicit public receipt
schema when replacing the seam with D1/DO.

For the server-boundary cases, the exact isolated harness used:

```bash
node --input-type=module <<'EOF'
import { stageAction, sha256, canonicalJson } from "./partners/watch/action-contract.js";
import { onRequestPost as stagePost } from "./partners/watch/functions/api/stage-interest.js";
import { onRequestPost as commitPost } from "./partners/watch/functions/api/register-interest.js";
import { commitInterest, stageInterest, summary } from "./partners/watch/functions/api/_store.js";
import { INTEREST_PRODUCT_SKUS, INTEREST_PRODUCTS } from "./partners/watch/interest-products.js";

const sku = INTEREST_PRODUCTS[0].sku;
const env = { WATCH_WRITE_MODE: "local-development" };
const origin = "https://watch.invalid";
const req = (path, body, session = "session-a") =>
  new Request(origin + path, {
    method: "POST",
    headers: { "content-type": "application/json", "x-watch-session": session },
    body: JSON.stringify(body),
  });
const action = await stageAction({
  payload: { product: sku, pricePoint: "100.50" },
  validSkus: INTEREST_PRODUCT_SKUS,
});
const staged = await stagePost({
  request: req("/api/stage-interest", { action }),
  env,
});
const stagedBody = await staged.json();
const first = await commitPost({
  request: req("/api/register-interest", {
    action,
    grantId: stagedBody.grantId,
    confirmationGrant: stagedBody.confirmationGrant,
  }),
  env,
});
const replay = await commitPost({
  request: req("/api/register-interest", {
    action,
    grantId: stagedBody.grantId,
    confirmationGrant: stagedBody.confirmationGrant,
  }),
  env,
});
const changed = {
  ...action,
  semanticPayload: { ...action.semanticPayload, targetPriceMinor: 99999 },
};
changed.semanticPayloadHash = await sha256(canonicalJson(changed.semanticPayload));
const conflict = await commitPost({
  request: req("/api/register-interest", {
    action: changed,
    grantId: stagedBody.grantId,
    confirmationGrant: stagedBody.confirmationGrant,
  }),
  env,
});
console.log(JSON.stringify({
  stage: staged.status,
  first: first.status,
  replay: replay.status,
  replayed: (await replay.clone().json()).replayed,
  conflict: conflict.status,
}));
EOF
```

The concurrency probe used two `Promise.all` calls to `commitInterest()`
with two distinct staged actions and then two calls with the same staged action
and key. Observed results were:

```text
distinct: ["committed","committed"], +2 records
same-key: ["committed","committed"], +2 records
```

Expected same-key result is one committed action and one exact replay (or an
equivalent serialized outcome), never two records.

## Recommendation

Keep the browser staging and fail-closed behavior. Before GO, replace the
local repository with an atomic D1 transaction or serialized Durable Object
that consumes the grant, claims the idempotency key, inserts the interest, and
persists the receipt as one operation; then rerun the full write matrix and a
fresh production-boundary acceptance run.
